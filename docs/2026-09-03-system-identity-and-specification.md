## 1. 시스템의 요점과 이름: 왜 "Argus Pulse"인가?

### 1) 시스템 명칭의 의미
* **Argus (아르고스)**: 그리스 신화에 등장하는 **'100개의 눈을 가진 잠들지 않는 파수꾼'**에서 유래했습니다. 24시간 쉬지 않고 글로벌 뉴스, 증권사 리포트, 블로그, 트위터를 전방위로 감시하는 지능형 레이더를 상징합니다.
* **Pulse (펄스)**: 단순한 텍스트 수집에 그치지 않고, 시장의 요동치는 **맥박(Market Pulse)**과 사용자가 추적하는 **투자 가설(Thesis)의 신호 강도**를 실시간으로 측정하여 살아 숨 쉬는 콘텐츠로 전환함을 의미합니다.

### 2) 시스템의 핵심 요점 (한 문장 정의)
> **"수많은 시장 노이즈 속에서 내 투자 가설(Thesis)을 검증·발전시키는 신호(Signal)만을 포착하여, 심층 블로그·스레드·다이제스트로 생산하고 옵시디언 영구 지식 자산으로 축적하는 개인화 인텔리전스 엔진"**

## 2. 사용자의 핵심 질문에 대한 해답 (Q&A)

### Q1. 데이터를 RAG에 저장 vs 옵시디언에 저장, 무엇이 더 좋은가?
> **답변: "옵시디언(Markdown)을 단일 진실 소스(SSOT)로 두고, 로컬 RAG가 이를 색인하는 하이브리드 구조가 압도적으로 우수합니다."**

| 구분 | 옵시디언 (Obsidian) | 상용 클라우드 RAG (Pinecone 등) | Argus Pulse 채택 방식 |
|---|---|---|---|
| **데이터 주권** | 로컬 Markdown 파일 (완전한 개인 소유) | 외부 서버 DB 종속 | **옵시디언 로컬 마크다운** |
| **인간의 가독성** | 사람이 직접 읽고, 수정하고, 링크 걸기 최적화 | 벡터 숫자 배열로 사람이 직접 검토 불가 | **옵시디언 뷰어 + 그래프 뷰** |
| **운영 비용** | **0원** (무료) | 매월 호스팅비 및 벡터 쿼리 비용 발생 | **0원** (로컬 SQLite/Chroma) |
| **LLM 연동** | 파일이 수백 개로 늘어나면 검색 한계 | 시맨틱 의미 기반 초고속 청크 추출 | **로컬 임베딩(RAG)으로 필요 시 자동 주입** |

* **결론**: 데이터를 RAG에만 가두면 내가 직접 열어볼 수 없는 '블랙박스'가 됩니다. **모든 원천 데이터와 생성물은 사용자의 옵시디언 마크다운으로 저장**되며, 시스템 내부 RAG 모듈([`rag_engine.py`](file:///Users/chansoojeon/Library/CloudStorage/Dropbox/03_code/b_0901_Argus_pulse/rag_engine.py))이 이를 비용 없이 로컬에서 읽어 LLM에게 주입합니다.

### Q2. 시스템을 LLM 위키 형태로 만드는 것이 좋은가, RAG로 기존 방식을 따르는 것이 좋은가? (비용 문제 고려)
> **답변: "Thesis 파일이 위키의 핵심 개념 페이지(Concept Page) 역할을 하는 'Thesis-Centric 위키' 구조가 정답입니다."**

* **비용 문제 해결**: 외부 LLM API로 수만 페이지의 문서를 매번 검색하면 비용이 폭발합니다.
* **Argus Pulse의 위키-RAG 설계**:
  1. `thesis/T-01~T-09.md`는 각각이 **위키 백과사전의 표제어**입니다.
  2. 매일 생산되는 블로그, 스레드, 수집 뉴스는 위키의 각 테제 문서에 **`[[백링크]]`**로 자동 연결됩니다.
  3. LLM은 글을 작성할 때 방대한 전체 문서를 뒤질 필요 없이, 해당 테제 위키 페이지의 핵심 가설과 연결된 증권사 리포트 요약 청크만 국소적으로 참조(Focused RAG)하므로 **API 토큰 비용이 80% 이상 절감**됩니다.

### Q3. 블로그 주제 추천이 매시간 모니터링 뉴스에 의해서 결정되는 것 맞는가?
> **답변: "맞습니다. 매시간 감시(Watcher)와 정기 정리(Synthesizer)가 유기적으로 결합되어 작동합니다."**

```
[24시간 실시간 감시 (hourly_monitor)]
  - 매시간(09:00~21:00) 증권/테크 뉴스 수집
  - 80점 이상 충격 뉴스 발생 시: 텔레그램/OS 알림 즉시 발송
         │ (누적 저장: news.sqlite)
         ▼
[정기 테마 추천 & 집계 (topic_generator / daily_digest)]
  - 아침 08:00: 밤사이 누적된 뉴스와 9대 Thesis를 교차 분석하여 '오늘의 콘텐츠 추천 3선' 제시
  - 오후/저녁: 긴급 변곡점 및 하루 누적 시장 반응을 테제별로 묶어 다이제스트 요약
```

### Q4. Thesis는 "내가 관심 있는 방향"을 좁혀주는 필터 역할인가?
> **답변: "정확합니다. Thesis는 끝없는 정보의 바다에서 가치를 추출하는 '지능형 프리즘'입니다."**

* 단순 키워드 검색(예: "반도체", "AI")은 하루 수천 건의 쓰레기 기사를 긁어옵니다.
* Thesis는 **방향성(Direction)**과 **가설(Hypothesis)**을 갖습니다:
  - 예: *"데이터센터 병목이 GPU에서 전력·냉각 인프라로 이동한다(T-01)"*
  - 예: *"추론 시대로의 전환으로 엔비디아 독점이 TPU와 커스텀 ASIC으로 분산된다(T-06)"*
* 시스템은 뉴스를 볼 때 **"이 뉴스가 내 가설(T-01~T-09)을 지지하는가, 반박하는가?"**의 관점으로만 스코어링하고 필터링합니다.

### Q5. 블로그 외에 주제만 잡고 그냥 문자 나열(스레드/아이디어 단상)도 좋을까?
> **답변: "매우 좋습니다. 실제로 스레드(Thread Writer) 및 마이크로 팩트 시트 모듈을 구축 완료했습니다."**

* 매번 2-Page 분량의 완결형 블로그를 읽거나 쓸 필요는 없습니다.
* **문자 나열형 포맷(Thread / Micro Note)**:
  - 13~15개의 핵심 팩트 문장 번호 나열 (예: `1. 사실 확인`, `2. 수치 증명`, `3. 구조 변화`)
  - 모바일에서 1분 만에 스크롤하며 읽을 수 있는 극도의 정보 밀도
  - X(구 트위터), 링크드인, 텔레그램 채널에 바로 복사해 올릴 수 있는 기동성

### Q6. 핵심 산출 범위는 무엇인가? (보고서 및 산출물 종류)
현재 시스템이 생성하는 4대 산출물:

1. **2-Page 심층 분석 블로그 ([`output/blog/`](file:///Users/chansoojeon/Library/CloudStorage/Dropbox/03_code/b_0901_Argus_pulse/output/blog))**:
   - 제목 3종 변형(직관/도발/스토리), 훅, 서론, 본론1, 본론2(반론 검토), 결론(투자 관점 & 관전 포인트), 데이터 박스, 엄격한 출처 각주
   - Critic 에이전트가 80점 이상으로 채점할 때까지 자가 보완 루프 실행
2. **팩트 스레드 ([`output/thread/`](file:///Users/chansoojeon/Library/CloudStorage/Dropbox/03_code/b_0901_Argus_pulse/output/thread))**:
   - 10~15줄의 번호 매겨진 구어체 팩트 타래
   - A각도(수혜/수치 중심), B각도(구조 변화), C각도(공장/리스크) 선택 가능
3. **일일 인텔리전스 다이제스트 ([`output/digest/`](file:///Users/chansoojeon/Library/CloudStorage/Dropbox/03_code/b_0901_Argus_pulse/output/digest))**:
   - 저녁 21:00 하루 전체 뉴스를 9대 테제별로 묶어내는 브리프
4. **과거 가설 검증 리뷰 ([`output/review/`](file:///Users/chansoojeon/Library/CloudStorage/Dropbox/03_code/b_0901_Argus_pulse/output/review))**:
   - 새로운 핫 뉴스가 없는 날, 2~4주 전 작성한 블로그의 예측을 현재 시점에서 역검증
