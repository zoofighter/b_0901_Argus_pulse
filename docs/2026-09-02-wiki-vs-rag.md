# LLM 위키 vs RAG — 어떤 방식이 좋은가?

> **날짜**: 2026-09-02  
> **배경**: Argus Pulse 시스템의 지식 저장 방식 결정

---

## 한 줄 결론

> **Argus Pulse에는 "RAG + 옵시디언 위키" 하이브리드**가 최적.  
> 비용을 아끼면서도 지식이 축적되는 구조를 만들 수 있다.

---

## 1. 두 방식의 차이 (쉬운 비유)

| | LLM 위키 | RAG |
|---|---|---|
| **비유** | 📚 백과사전을 미리 만들어 놓고 찾아 읽는 것 | 🔍 필요할 때마다 도서관에서 관련 자료를 검색하는 것 |
| **언제 비용 발생** | 자료를 넣을 때 (정리·요약·연결) | 질문할 때마다 (검색·조합·응답) |
| **장점** | 잘 정리된 지식, 빠른 응답 | 항상 최신 데이터, 구축이 간단 |
| **단점** | 새 자료 추가 시 재정리 필요 | 매 질문마다 토큰 비용 |

---

## 2. 각 방식이 문서를 읽는 시점

### 핵심 차이: LLM이 문서를 "언제, 몇 번" 읽는가

```
┌─────────────────────────────────────────────────────────────────┐
│                        LLM 위키 방식                            │
│                                                                 │
│  [인제스트]                      [질문/보고서 생성]              │
│  원본 PDF 30페이지 (15000자)     위키 요약본 2페이지 (2000자)    │
│       ↓                              ↓                          │
│  🧠 LLM이 읽고 요약 (1회)       🧠 LLM이 요약본만 읽음 (매번)   │
│       ↓                              ↓                          │
│  📝 위키 문서 저장               💬 보고서 생성                  │
│                                                                 │
│  💰 여기서 비용 발생 (높음)      💰 여기서 비용 발생 (낮음)      │
│     → LLM이 원문 전체를 읽으므로    → 요약본만 읽으므로           │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                        RAG 방식                                 │
│                                                                 │
│  [인제스트]                      [질문/보고서 생성]              │
│  원본 PDF 30페이지 (15000자)     검색된 원문 조각들 (~5000자)    │
│       ↓                              ↓                          │
│  ✂️ 기계적으로 쪼개기 (LLM 안 씀)  🧠 LLM이 원문 조각을 읽음 (매번)│
│       ↓                              ↓                          │
│  💾 벡터 DB에 임베딩 저장         💬 보고서 생성                 │
│                                                                 │
│  💰 여기서 비용 거의 없음        💰 여기서 비용 발생 (높음)      │
│     → LLM을 안 쓰므로              → 매번 원문을 읽으므로        │
└─────────────────────────────────────────────────────────────────┘
```

### 구체적 예시: "HBM 산업 보고서" PDF 30페이지

**① LLM 위키 — 인제스트 단계 (1회만 실행)**
```
원본 PDF (30페이지, 15000자)
    ↓ LLM이 읽고 요약 ← 여기서 비용 발생
위키 문서 (2페이지, 2000자)로 저장
    예: "HBM_산업_요약.md"
    - 핵심 논점 3가지
    - 주요 수치 정리
    - 관련 종목 영향
```

**② LLM 위키 — 보고서 생성 시 (매번)**
```
LLM이 읽는 것:
  ❌ 원본 PDF 30페이지 (15000자) ← 안 읽음
  ✅ 위키 요약 2페이지 (2000자)  ← 이것만 읽음
  → 원본 대비 약 87% 토큰 절약
```

**③ RAG — 보고서 생성 시 (매번)**
```
LLM이 읽는 것:
  ✅ 검색된 원문 조각 5~10개 (~5000자) ← 매번 읽음
  → 위키 방식보다 2.5배 더 많은 토큰 소비
```

### 보고서 10번 생성 시 LLM이 읽는 총량

| | LLM 위키 | RAG |
|---|---|---|
| 인제스트 시 | 15,000자 (1회) | 0자 |
| 보고서 10회 | 2,000 × 10 = 20,000자 | 5,000 × 10 = 50,000자 |
| **합계** | **35,000자** | **50,000자** |
| **100회면** | **215,000자** | **500,000자** |

→ 반복할수록 LLM 위키가 유리해지는 구조

## 3. 비용 비교

### LLM 위키 방식

```
[자료 투입 시]                    [질문 시]
PDF 30장 → LLM이 읽고 요약       → 정리된 위키를 읽기만 하면 됨
웹 200장 → 서로 연결·구조화       → 토큰 비용 적음
                                
💰 초기 비용: 높음                 💰 운영 비용: 낮음
   (LLM으로 30+200장 처리)           (이미 정리된 것을 읽으므로)
```

**비용 추정** (Gemini Flash 기준):
- 초기 구축: PDF 30장 + 웹 200장 ≈ **약 $2~5** (1회성)
- 유지: 새 자료 추가할 때마다 소액 발생
- 질문 응답: 거의 무시할 수준

### RAG 방식

```
[자료 투입 시]                    [질문 시]
PDF 30장 → 쪼개서 벡터 저장       → 관련 조각 검색 + LLM에 전달
웹 200장 → 쪼개서 벡터 저장       → 매번 검색 + 응답 비용
                                
💰 초기 비용: 낮음                 💰 운영 비용: 누적됨
   (임베딩만 하면 됨)                (1시간마다 보고서 × 하루 24회)
```

**비용 추정** (Gemini Flash 기준):
- 초기 구축: 임베딩 비용 ≈ **약 $0.5** (1회성)
- 1회 보고서 생성: 검색 + LLM 응답 ≈ **약 $0.01~0.03**
- 하루 24회 × 30일 = 720회/월 ≈ **약 $7~20/월**

### 비용 비교표

| 항목 | LLM 위키 | RAG | 하이브리드 |
|---|---|---|---|
| 초기 구축 | $2~5 | $0.5 | $2~5 |
| 월 운영 (보고서 24회/일) | $1~3 | $7~20 | $3~8 |
| 6개월 총비용 | **$8~23** | **$42~120** | **$20~53** |
| 자료 추가 시 | 재정리 비용 | 임베딩만 추가 | 혼합 |

### 손익분기점

```
보고서 생성 횟수:
  ~50회:   RAG가 약간 저렴 (초기 비용 차이)
  ~100회:  비슷해짐 (손익분기)
  ~200회+: LLM 위키가 확실히 저렴
  
1시간마다 생성 시: 약 4~8일 만에 LLM 위키가 역전
```

## 4. ⚠️ 위키의 함정 — 쌓이면 결국 RAG가 필요해진다

### 위키 문서가 많아지면 생기는 문제

위키가 소규모일 때는 전체를 LLM에 넣어도 됩니다. 하지만 **문서가 쌓이면 결국 "어떤 위키 문서를 읽을 것인가"를 선택해야 합니다**:

```
위키 문서 10개   → 전부 LLM에 넣어도 됨 (약 20,000자, 비용 적음)
위키 문서 50개   → 전부 넣으면 100,000자 → 비용 부담 시작
위키 문서 100개  → 전부 넣으면 200,000자 → 비용 커짐
위키 문서 500개  → 전부 넣는 건 불가능    → "검색"이 필수
```

### 위키 문서 선택 방법 3가지

```
방법 1: 사람이 직접 고름       → 수동, 번거로움, 확장 불가
방법 2: 키워드/태그로 필터     → 단순하지만 관련 문서를 놓칠 수 있음
방법 3: 벡터 검색으로 자동 선택 → 이것이 결국 RAG와 동일한 구조
```

### Argus Pulse의 위키 증가 속도

```
초기:    PDF 30건 + 웹 200건 요약 = ~230개 위키 문서
1개월:   심층 보고서 24/일 × 30 = +720개
3개월:   +2,160개
6개월:   +4,320개
합계:    6개월 후 약 4,550개 위키 문서
```

→ **첫 달부터 위키 문서가 950개** 이상. 전부 LLM에 넣는 것은 불가능.
→ 따라서 위키 요약본을 벡터 DB에 넣고 검색하는 구조가 필수.

### 핵심 깨달음

> **위키와 RAG는 대립하는 것이 아니라, 규모가 커지면 결국 합쳐지는 구조**

```
소규모 (문서 ~50개):   위키만으로 충분. 전부 읽어도 됨.
중규모 (문서 ~200개):  위키 + 간단한 태그 필터링
대규모 (문서 500개+):  위키 요약본을 벡터 DB에 넣고 검색 ← 결국 RAG
```

## 5. Argus Pulse에 적용하면?

### ❌ LLM 위키만 사용 — 적합하지 않음

- 실시간 뉴스가 매시간 바뀜 → 위키를 매번 업데이트해야 함
- 첫 달부터 문서 950개+ → 전부 읽는 것 불가능
- 뉴스는 "정리"보다 "검색"이 중요

### ❌ RAG만 사용 — 가능하지만 비효율

- 매번 230+장의 자료에서 검색 → 컨텍스트 비대
- 같은 배경 지식을 매 질문마다 반복 검색
- 월 비용이 점점 증가 ($7~20/월)

### ✅ 하이브리드 — 최적

**안정적인 지식 = 위키 (LLM이 1회 정리)**, **변동하는 데이터 = RAG (매번 검색)**로 분리:

```
┌──────────────────────────────────────────────────────────┐
│              Argus Pulse 하이브리드 구조                   │
│                                                          │
│  📚 위키 레이어 (옵시디언에 마크다운 저장)                  │
│  ├─ 산업 PDF 요약 → LLM이 1회 정리한 마크다운              │
│  ├─ 웹 자료 핵심 정리 → 주제별 구조화                      │
│  ├─ Thesis 배경 지식 → 가설별 정리                        │
│  └─ 과거 보고서 → 축적된 인사이트                          │
│  → 변경 빈도: 낮음 (주 1~2회 업데이트)                    │
│  → 위키 요약본도 ChromaDB에 저장하여 검색 가능              │
│                                                          │
│  🔍 RAG 레이어 (ChromaDB + SQLite)                        │
│  ├─ 위키 요약본 벡터 검색 (문서 많아져도 관련 것만 선택)    │
│  ├─ 실시간 뉴스 (SQLite에서 최신 고득점만 조회)            │
│  └─ 최근 생성 보고서 검색                                  │
│  → 변경 빈도: 높음 (매시간)                               │
│                                                          │
│  보고서 생성 시 흐름:                                      │
│  1. RAG로 관련 위키 요약본 5~10개 검색 (전부 안 읽음)       │
│  2. RAG로 최신 뉴스 10~15개 검색                           │
│  3. LLM에게 검색된 것만 전달 → 보고서 작성                  │
│  → 토큰 비용 = 위키 요약 ~10,000자 + 뉴스 ~5,000자        │
│  → RAG 단독 (~15,000자) 대비 품질은 높고 비용은 비슷       │
└──────────────────────────────────────────────────────────┘
```

### 비용 절감 효과

| 방식 | 보고서 1회 비용 | 이유 |
|---|---|---|
| RAG만 | $0.01~0.03 | 매번 원문 조각 검색 + 긴 컨텍스트 |
| **하이브리드** | **$0.005~0.01** | 요약본 검색 (더 짧고 밀도 높음) |

→ **약 50~60% 비용 절감** (더 짧지만 밀도 높은 요약본을 읽으므로)

## 6. 옵시디언 위키의 역할

옵시디언은 **LLM 위키의 저장소**이자 **사람의 인터페이스** 역할을 함:

| 역할 | 설명 |
|---|---|
| 📖 사람이 읽는 지식 | 보고서·요약을 마크다운으로 열람 |
| 🤖 AI가 읽는 지식 | 보고서 생성 시 배경 컨텍스트로 활용 |
| 🔗 지식 연결 | 옵시디언의 `[[링크]]`로 주제 간 연결 |
| 📂 아카이브 | 모든 산출물의 영구 저장소 |

## 7. 최종 권장안

```
산업 PDF (30장)  ──→  LLM이 요약·정리(1회) ──→  옵시디언 위키 (마크다운)
웹 자료 (200장)  ──→  LLM이 요약·정리(1회) ──→  옵시디언 위키 (마크다운)
                                                     ↓
                                            요약본을 ChromaDB에도 저장
                                                     ↓
실시간 뉴스 ──→ SQLite ──→──────────→ RAG 검색과 결합
                                                     ↓
                                            LangGraph 멀티에이전트
                                                     ↓
                                            보고서 생성 (4종)
                                                     ↓
                                            옵시디언 저장 + 디스코드 전송
                                                     ↓
                                            생성된 보고서도 위키에 축적 🔄
                                                     ↓
                                            요약본 ChromaDB에 재인제스트 🔄
```

### 핵심 판단

| 질문 | 답 |
|---|---|
| 위키만 쓸까? | ❌ 실시간 뉴스 대응 불가 + 문서 쌓이면 전부 못 읽음 |
| RAG만 쓸까? | ❌ 가능하지만 비용 비효율 |
| **둘 다 쓸까?** | **✅ LLM이 정리한 위키 요약본을 RAG로 검색하는 구조** |
| 비용은? | 하이브리드가 RAG 단독 대비 **약 50% 절감** |
| 옵시디언은? | 위키 저장소 + 사람이 읽는 인터페이스 |
| 위키가 커지면? | 위키 내에서도 RAG 검색 → 자연스럽게 확장 |
